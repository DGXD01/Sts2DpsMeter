## 2. 问题与改进

### 2.1 过长内容可能撑大面板

原布局虽然给面板尺寸设置上限，但明细容器的最小高度可能大于该上限，原生容器仍可能把面板撑出屏幕。多模块、MaxRows 较大或 UiScale 较大时更容易出现。

本轮将明细放入垂直滚动容器，以布局计算结果约束可见明细高度；标题、范围、齿轮和折叠按钮保留在滚动区域外。较少明细按内容收缩，超长明细滚动查看，不把全部内容高度强加给面板。切换范围、玩家及新战斗时回到明细顶部；普通伤害刷新保留滚动位置。

布局尺寸计算拆为同一 UI 内部的 `DpsHudLayout`，不访问场景树、不新建统计系统。输入原生测得的标题/边框尺寸、内容高度、视口和 UiScale，输出面板尺寸、位置与明细可见高度。

### 2.2 无变化时仍在测量数字列

原行节点池避免了重建，但每次刷新仍测量所有可见行的数字文本。本轮缓存各行测量结果；数字文字、字号或字体主题通知变化时才重新测量，仍在所有可见行之间统一数字列宽。

可见行列表改为复用缓冲区。只有可见行结构、行高、列宽或布局配置变化时请求面板尺寸计算；已裁切的标题仅改变数字时不再单独触发尺寸重算。Snapshot 构造和排序仍有托管分配，本轮不宣称零分配或已取得实机性能提升数据。

### 2.3 复用行需要显式处理语言变化

行缓存新增语言标识。即使来源数据本身相同，语言变化也会重建该行的富文本内容，避免本地玩家标记等局部文字继续使用旧语言；保持职业颜色及 BBCode 转义。
