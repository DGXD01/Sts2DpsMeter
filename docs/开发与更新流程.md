# 开发与更新流程

## 1. 工作类型与分支

每个变更先确定类型，再创建或切换到对应分支。分支名使用英文类型前缀，描述可以使用稳定的功能名；禁止使用 `codex/` 前缀。

| 类型 | 分支示例 |
| --- | --- |
| 新功能 | `feature/CombatPanel` |
| Bug 修复 | `fix/DamageAttribution` |
| 文档 | `docs/ReleaseGuide` |
| 重构 | `refactor/StatsService` |
| 性能优化 | `perf/LogBatching` |
| 测试 | `test/DamageStats` |
| 构建、流程 | `chore/Sts2DpsMeterBootstrap` |

主分支不直接推送。修改者从最新 `main` 创建分支；同步主分支时必须使用 `merge`，禁止 `rebase`。

## 2. 开发验证

提交前至少完成：

```powershell
pwsh -NoProfile -File .\scripts\validate-repo.ps1
```

有游戏环境时再执行：

```powershell
$env:STS2_GAME_DIR = 'D:\SteamLibrary\steamapps\common\Slay the Spire 2'
pwsh -NoProfile -File .\scripts\build-and-stage.ps1
```

运行态验证必须记录：

- 游戏版本、Mod 版本、单人/多人模式；
- 测试角色、战斗房间或种子；
- 预期结果、实际结果；
- Godot 日志中与 `[Sts2DpsMeter]` 相关的行；
- 失败时的完整异常或复现步骤。

## 3. 版本同步

每次可发布变更必须同步以下位置：

1. `Sts2DpsMeter.csproj` 的 `<Version>`；
2. `manifest.json` 的 `version`；
3. `CHANGELOG.md`；
4. `workshop/workshop.json` 的 `changeNote`；
5. 如果发布，创建与版本一致的 Git 标签，例如 `v0.2.0`。

`has_pck` 当前为 `false`，因为项目尚未包含 PCK 资源。增加资源包后必须同步修改清单和构建脚本。

## 4. GitHub 变更控制

本仓库的阶段规则：

- 一个阶段只使用一个 PR；
- 新建 PR 前在本地 `merge` 最新 `main`；
- commit、push、创建 PR、合并 PR 分别取得明确授权；
- 没有明确授权，不向 PR 或 Issue 发表评论；
- PR 正文和评论使用中文；
- 审查后如果发生实质修改，重新提供修改清单、Diff 摘要、验证结果和风险。

## 5. Steam 创意工坊发布

使用官方上传器 [megacrit/sts2-mod-uploader](https://github.com/megacrit/sts2-mod-uploader)。

### 首次上传

1. 运行一次 `ModUploader.exe`，生成工作区结构。
2. 将本仓库 `workshop/content/` 中的 DLL 和 JSON 放入上传器工作区。
3. 填写 `workshop.json` 和小于 1 MB 的 `image.png`。
4. 确认 `visibility` 为预期值；首次测试建议保持 `private`。
5. 在已登录 Steam 的 Windows 机器上执行：

```powershell
.\ModUploader.exe upload -w .\Sts2DpsMeter
```

6. 上传器生成 `mod_id.txt` 后，将该文件提交到本仓库，禁止删除或手工修改。

### 后续更新

1. 更新版本号和更新日志。
2. 执行构建脚本，刷新 `workshop/content/`。
3. 检查 `workshop.json` 的 `changeNote`。
4. 保留已有的 `mod_id.txt`，执行上传命令。
5. 在 Steam 页面确认更新说明和版本文件是否正确。

Steam 凭据、登录状态和上传器日志不得进入 Git 仓库，也不能放到 CI 中自动发布。

## 6. 回滚原则

- 不使用 `rebase` 或强制推送。
- 发现发布错误时，先用 `git revert` 创建可审查的回滚提交。
- 已经上传到 Steam 的版本，重新上传一个修复版本，不依赖改写 Git 历史。
- 保留 `mod_id.txt`，避免误建新的创意工坊条目。
